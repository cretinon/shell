## 2. Findings

### 🟠 Medium

#### M1 — `_process_opts` returns `0` (success) on unknown/bad options
- **File:** `lib_shell.sh:308`
- **Code:**
  ```bash
  OPTS=$(getopt ...) || (_error "Bad or missing argument..."; _func_end "1" ; return 1)
  ```
- **Problem:** the `( … )` block is a **subshell**. `_func_end "1" ; return 1` therefore only affects the subshell; it never propagates out of `_process_opts`. Execution continues into the `else` branch (`eval set -- "$OPTS"`), the option loop hits the `--` terminator that `getopt` emitted, and the function falls through to `_func_end "0" ; return 0`.
- **Verified:**
  - `_process_opts --bogus` → prints *"Bad or missing argument"* but **returns 0**
  - `_process_opts -x` → **returns 0**
- **Impact:** contradicts the documented contract (`functions.md`: *"1 — bad/missing argument"*). The CLI *appears* to fail only because `_main` later returns 1 via the no-`LIB` usage path — a coincidence that masks the bug. Any code calling `_process_opts` directly (or a future action) would treat a malformed invocation as success.
- **Fix:** capture the failure in the parent scope, e.g.
  ```bash
  if ! OPTS=$(getopt ... 2>/dev/null); then
      _error "Bad or missing argument..."; _func_end "1" ; return 1
  fi
  ```

#### M2 — `_date_2_epoch` is not UTC despite its comment and `functions.md`
- **File:** `lib_shell.sh:653` (`# always return UTC epoch`) and `functions.md` (*"Converts a date string to a UTC epoch timestamp"*).
- **Problem:** `date -d "$1" +"%s%3N"` has **no `-u`**, so it interprets the input in the *local* timezone. The sibling `_epoch_2_date` does use `-u`, so round-trips are inconsistent off-UTC.
- **Verified:**
  - `TZ=UTC date -d "2024-04-05 21:34:38" +%s` → `1712352878`
  - `TZ=America/New_York date -d "2024-04-05 21:34:38" +%s` → `1712367278` (**+4 h**)
- **Fix:** use `date -u -d "$1" +"%s%3N"` (or fix the docs if local-time interpretation is intended).
